Setting up, running and maintaining the Ragnarok Rebuild fork

Everything is driven by one helper, rr, in the repo root. It wraps the git fork wiring, the Unity CLI, our own resource pack built from several kRO clients, the .NET server and headless Unity imports and builds. Every command is safe to rerun.

TL;DR

Once setup has run, day to day you only need these:

.\rr server            # terminal 1: game server on ws://127.0.0.1:5000/ws
.\rr editor            # open Unity, Ragnarok > Open Main Scene, press Play, log in
.\rr sync              # pull Doddler's latest changes into your branch
.\rr doctor            # health check: git, tools, data, import state, disk, half-done work

On a new machine, one line in PowerShell does everything, even with nothing installed. It installs Git if it's missing, clones the fork on dev and runs rr setup. Setup asks for a work folder and your client GRFs, installs the missing tools after one question, then does the rest. Our own rebuild-pack.grf is enough on its own (details):

irm https://raw.githubusercontent.com/geocine/RagnarokRebuildTcp/dev/setup/bootstrap.ps1 | iex

With Git already installed, the same by hand:

git clone -b dev https://github.com/geocine/RagnarokRebuildTcp.git
cd RagnarokRebuildTcp
.\rr setup             # init, prereqs, git-setup, install-unity, library-link, server-build, update-client, pack, import

To skip rr init's questions, copy setup\config.local.example.json to setup\config.local.json and set your own paths; rr setup then asks nothing. With a snapshot in the work folder that matches the pack, rr setup restores it instead of importing: about 10 minutes instead of an hour and a half.

.\rr build-client      # Windows player (IL2CPP) into workDir\Build\PC
.\rr smoke             # proves it works: server + build log in, create a character, enter the world
.\rr release           # shareable Client + Server download like Doddler's, checked before it's zipped

What lives where

The repo can live anywhere; it grows to about 11 GB with the imported client. Everything rr generates goes into one work folder (workDir) outside the repo, and the client GRFs are only read, wherever they are.

Keep the Unity Library on an internal SSD. With the Library on a USB drive, the import was disk-bound (the drive at 100% busy, Unity mostly idle). On an internal SSD Unity is CPU-bound and the disks sit idle. rr library-link <folder> moves it, junction included, and rr perf adds Defender exclusions for the project, Library and pack (rr perf undo removes them).

Each command also checks its own tools before it starts (rr server checks .NET, rr build-client the C++ toolchain), so a missing tool gets the same install offer instead of a "not recognized" error. rr doctor lists missing tools and points to rr prereqs.

Free space for a full setup: about 13 GB on C: for Unity (7 GB more for the Build Tools), 11 GB in the repo for the imported assets, 10 GB for the Library and 3 GB for the pack. Player builds later add about 25 GB to the work folder, and each snapshot 15 GB.

Use the standalone Unity CLI, not the winget build. winget install Unity.CLI installs an MSIX package. Its sandbox virtualizes AppData, so the editor installer it launches aborts silently ("exited with code 2"). rr install-unity swaps it for the build from https://unity.com/install.ps1 in %LOCALAPPDATA%\Unity\bin, which runs installers normally.

First-time setup

From a bare machine

setup\bootstrap.ps1 is one file that runs before anything is installed, Git included, in the Windows PowerShell 5.1 that ships with Windows:

irm https://raw.githubusercontent.com/geocine/RagnarokRebuildTcp/dev/setup/bootstrap.ps1 | iex

To pick the folder up front and skip the install question:

& ([scriptblock]::Create((irm https://raw.githubusercontent.com/geocine/RagnarokRebuildTcp/dev/setup/bootstrap.ps1))) -Dir D:\RagnarokRebuildTcp -Yes
  • It installs Git with winget if it's missing, then asks where to clone. It suggests the fixed drive with the most free space, because the repo grows to about 11 GB with the imported client, and warns about folders inside OneDrive.
  • It clones dev over HTTPS (no SSH key needed) with core.autocrlf=input and long paths on, then runs rr setup.
  • Run it again after an interruption: it reuses the clone and setup carries on. A clone that was cut off before its checkout is cloned again.
  • -Repo and -Branch clone another URL or branch.
  • Tested in Windows PowerShell 5.1: a fresh clone into an empty folder, a clone cut off before its checkout, and a rerun on a setup that was stopped during the server build.

Everything that needs you happens first: rr init's questions, the install question and the administrator prompts, then the Unity browser sign-in if it's needed. The downloads, builds, pack and import after that run unattended.

The steps

.\rr setup runs all of this in order. The individual steps are listed so you can rerun one when something changes.

  1. Paths — .\rr init asks for the work folder (it suggests the local drive with the most free space), your client GRFs in priority order, the BGM folder and Doddler's release archive, then writes setup\config.local.json. Given a rebuild-pack.grf, it stops after that one source.
  2. Prerequisites — .\rr prereqs checks the tools and free space, and installs what's missing with winget after one question. Details.
  3. Git — .\rr git-setup points origin at the fork (forkUrl in setup\config.json) and upstream at Doddler with pushing disabled. It also creates the dev branch, installs the master/main guard hooks and sets core.autocrlf=input.
  4. Unity — .\rr install-unity installs the standalone CLI and the editor version from ProjectVersion.txt, plus Windows Build Support (IL2CPP) because ProjectSettings sets the Standalone backend to IL2CPP (240 MB; nothing else). Without an activated license, it signs you in before the download, so the rest runs unattended, then activates Unity Personal. It also checks for an MSVC toolchain and clears the ~4 GB installer cache.
  5. Server — .\rr server-build builds RoRebuildServer.sln.
  6. Shared data — .\rr update-client is updateclient.bat without the pause. It rebuilds GameConfig/RebuildSharedData, copies the DLLs into the client and regenerates StreamingAssets/ClientConfigGenerated. If you haven't touched the shared code, it puts the committed DLLs back so git stays clean.
  7. Library — rr library-link puts Unity's cache on the work drive behind a junction, so the repo can stay on a small disk.
  8. Pack — .\rr pack first runs rr reference (Doddler's walk data out of the release archive), then builds our own resource pack from every source. Details.
  9. Import — .\rr import full copies the pack's BGM into Assets\Music, then runs the upstream importers headlessly against the pack: raw copy, effects, water, every map, item and skill icons, then the addressables update. Details.
Unity batch mode can't share the project with an open editor. Close Unity before rr import, bake, build-client or report; rr checks and tells you.

Sources can be GRF 0x200 (every client here) or 0x300, the 64-bit format kRO has used since late 2025. The 0x300 reader was tested on a copy of our pack saved as 0x300 by GRF Editor 1.9.1.2's library: the pack built from it was byte-identical. Newer kRO GRFs can also mark entries with Gravity's new encryption (flag 0x80). No public tool decodes those, GRF Editor included, so the pack skips them and says how many it skipped; the files then have to come from another source.

Each file comes from the first source that has it, except maps. Maps are picked by comparing each candidate's walk data with the walk data in Doddler's release (601 files), which is what the live game uses. The tool recreates the importer's walk export byte for byte (.gat cell types plus the RSW water level), so an exact match proves the right map version. Otherwise the copy with the fewest cells whose walkable or line-of-sight flag differs wins, then the one with the fewest water-only differences, and source priority only breaks exact ties. The report counts them in cells ("3 of 57,600 cells differ", "only water differs (21 cells)"), because a percentage hides them: 3 cells on a big map round to 100.0%. A map's textures, models and sounds then come from the map's own source when it has them. When maps from different sources share a file, the higher-priority source's copy is used.

What it fixes along the way

  • Only what's used: monsters, NPCs, bodies, heads, headgear, icons and cut-ins come from the references, not whole folders. Cut-ins alone went from 1,764 files (854 MB) to the 17 that NPC scripts show.
  • Map versions: 83 maps match the release exactly and 38 differ only in water flags. For another 149 the release differs by a handful of hand-edited cells (at least 99% identical). For all of these, and for 2 server-only maps no client ships (poring_c01, poring_c02), the server gets Doddler's walk files: all 272 in walkdata\.
  • Older map versions: kRO has since redrawn izlude (the 2014 redesign is 268×300; the release's is 268×268), alberta and moc_ruins, so no current kRO client matches the release there. The 2009 client's alberta and izlude match it apart from water flags, and so does the classic client's moc_ruins. The two old clients' versions of 12 more maps are also closer: 4 of the 2009 client's 5 (prontera, prt_castle, yuno and the server-only alde_gld) match exactly or apart from water, and 5 of the classic client's 7 match exactly. So some cells that looked like hand edits were older map versions: kRO 2020's prontera and yuno differ from the release in 40 and 53 walkable cells, the 2009 copies in none. Seven more older copies are only a few cells closer than kRO 2024's, which a rounded percentage couldn't tell apart: cmd_fild03 (26 cells off, the classic client's 3), prt_fild00 (29, kRO 2020's 9), cmd_fild08 (the classic client's 43, the 2009 client's 16), gl_church (92 to 81), prt_fild05 (21 to 19) and mjolnir_01 (22 to 21). The classic client's pay_fild10 ties on walk cells and has fewer water differences. The RWC 2009 client (another build of the 2009 client, plus an event GRF with other versions of 8 towns) was tried as the lowest-priority source and isn't one: it ties or trails on every map, and its only files the others lack are 20 that nothing in Rebuild uses.
  • Renamed maps found by layout: payon_p (Old Payon) is kRO 2024's 1@exsh, pvp_n_1-4 is job_priest and pvp_n_1-5 is job_knight, all exact matches with the release. guild_room is quiz_01, which matches apart from water flags.
  • Newer map formats: the importer only reads RSW 2.1. aldeg_cas01 (RSW 2.2) and payon_p (RSW 2.6: water moved to the GND, and later builds add a byte per model, detected by parsing) are rewritten as exact 2.1 files. Kept the other way round, kRO 2024's redesigned payon would not import at all, so the 2020 copy is used.
  • Hair colours: headdata.json's <n>_남_<c> ids are palettes (palette\머리\머리<n>_남_<c>.pal), not sprites. Seven colour-0 palettes kRO never shipped are derived from the sprite's own embedded palette.
  • Map tables: fogparametertable.txt and mapobjlighttable.txt are included (fog and ambient per map).
  • GAT 1.3 water flag: payon_p's source (kRO 2024 1@exsh.gat, GAT 1.3) marks water tiles by setting bit 31 on the cell type (0x80000001 = water + blocked). The importer only knows types 0–6 and threw, so the map had no scene. The pack clears the flag (5,682 cells, only that map) and keeps the real type underneath. Nothing Rebuild uses is lost: all 5,682 cells are blocked in Doddler's own payon_p.walk too, the walk data matches his byte for byte, and the importer still finds the water from the RSW water level (it agrees with the flag on 5,617 cells, and every water cell is blocked either way).
  • Sounds Unity can't decode: 6 MS/IMA ADPCM .wav files (e.g. se_frog02.wav) failed in Unity's audio importer. They're decoded to 16-bit PCM in the pack.
  • Unpaired sprite halves: weapon, shield and effect folders are copied whole, and 15 files there are an .act without its .spr (or the reverse) in every client. They only produced import errors, so they're left out and listed in the report.
  • System files: folders copied whole skip Thumbs.db, desktop.ini, .DS_Store and Sound Forge .sfk peak files. kRO 2020 had three, and two had already been imported into Assets\Sounds and Assets\Sprites\Effects.
  • Sprite sound events: every ACT's event table is read and each sound checked at the exact wav\ path the importer loads. The only one no client has, spore_move.wav, gets a stand-in.

Extra files in the Custom folder

The fork's pack carries five things no client has from its Custom folder: two that Doddler shared, then a map, some item art and a music track from elsewhere. They're optional: a pack built without them is complete, and rebuild-pack.grf already has them.

  • His edited que_qsch01 (Okolnir) and prt_fild08, from MapEdits_southprontera+okolnir.unitypackage. The package can't be imported as is (its scripts are older than ours), so its edits were written once into the kRO map files. Cell types and heights went into the .gat, the ground's heights, textures and colours (recovered from his ground meshes) into the .gnd, and models added, moved or switched off into the .rsw. For que_qsch01 that's 2,837 cell types, 3,935 cell heights, 600 ground tiles raised or lowered, 144 repainted (the centre's grass and coloured tiles became the stone of the Frus and Skogul rooms), 88 models added and 103 moved or removed. For prt_fild08 it's 169 cell types, 9 heights, 43 ground tiles raised or lowered and 9 models; its ground keeps kRO's textures, since his repaint of 1,765 tiles along the edge with Prontera looked less right in game. Both maps then match his walk data apart from cells that are walkable without line of sight, which a .gat can't express (76 and 14; the client treats them as walkable), so the server uses his walk files. After import, both scenes reproduce the files exactly; Okolnir's ground matches his scene tile for tile, and prt_fild08's matches it in height. His Okolnir scene's skill markers (switched off in his release) and cloud layer aren't map data, so they're left out (Known gaps).
  • His 10 custom monster sprites. Four replace stand-ins (deathspore, fungus, deniro_larva, piere_larva). Four replace kRO 2024 files with the same names: kRO's soldier_deniro and soldier_piere are an unrelated monster that shows as a black silhouette, and his raptice and were_wolf have more animation frames. andre_larva and soldier_andre are identical to kRO's.
  • The 2009rwc_03 debug room (its .gat, .gnd and .rsw), the one client map no client has. Its 30 models and 9 textures come from kRO 2024. It matches the release's walk data apart from 472 water cells, so the server keeps the release's walk file. It came with 8 more RWC arena maps (2008rwc_04, 2009rwc_01, 02 and 04, 2012rwc_01 to 04) that Rebuild doesn't use, so the pack leaves them out.
  • Collection art for 7 skill scrolls (texture\유저인터페이스\collection\koko_*.bmp): Aspersio, and solo and party Assumptio, Blessing and Increase AGI. Their item icons came with them, but they're the same files as the repo's own in Assets/Textures/CustomIcons/Item, so only the collection art is needed.
  • Okolnir's music, bgm\ToS-3rdWave.flac: "3rd Wave" by Questrosound, from the Tree of Savior soundtrack. Maps.csv names it with its extension, and the client loads it by that exact name. It's Doddler's own copy, from his June 2025 release. A build doesn't keep the original FLAC: his holds Unity's Vorbis encoding of it at full quality (music_assets_assets\music\tos-3rdwave.flac.bundle), which was decoded with UnityPy and saved as FLAC (ffmpeg -i ToS-3rdWave.wav ToS-3rdWave.flac; 210.8 s, 26.1 MB). Unity re-encodes it with the same settings as the other tracks. An MP3 of the track also works (ffmpeg -i <file>.mp3 -map 0:a ToS-3rdWave.flac), but the one tried here was a different master: no silence before the music, where his has 0.75 s, and about 1 dB quieter.

Another machine from its own clients

If our GRF can't be shared, list your own clients in packSources and run rr pack. Every fix above is a rule rather than a list of our files: map verification, renamed-map search, RSW and GAT rewrites, ADPCM decoding, derived palettes, stand-ins, and the skipping of unpaired sprites and system files. The tool finds the same problems in any client.

What the result looks like depends on two things you supply:

  • Doddler's release archive (releaseArchive, read by rr reference). Without it maps are taken by source order and not verified, renamed maps such as payon_p are not found, and the server's walk files are built from your maps instead of Doddler's hand-edited ones.
  • Which clients you have. Files come only from them. A file none of them ships becomes a stand-in or is reported missing.

The fork's Custom folder adds files no client has (above). Without them, a pack has kRO's versions of que_qsch01 and prt_fild08, stand-ins or kRO's files for 8 monsters, no 2009rwc_03 for the client, item icons instead of collection art for 7 scrolls, and no music in Okolnir.

To show what that means in practice, each build compares its result with setup\pack\fingerprint.tsv, the fingerprint of the fork's pack. The fingerprint holds file names, SHA-1s and sources, never game data. The console and a "Compared with the fork's pack" section in report.html list the files that differ, are missing or are extra, maps that took a different version, and server walk files that differ. Differing and missing files are grouped by the fork source they came from, with its GRF version, so you know which client to add:

Run & play

  1. .\rr server starts the server with the RoRebuildServer launch profile (all maps). .\rr server Minimal loads only prt_fild08, which is handy for fast iteration. rr points the server at the pack's walkdata\ through the ServerDataConfig__WalkPathData environment variable, so no tracked config changes. Without a pack it falls back to RebuildClient/Assets/Maps/exportdata from the map import.
  2. .\rr editor opens the project through the Unity CLI. Pick Ragnarok > Open Main Scene, press Play and create an account at the login box. The client connects to ws://127.0.0.1:5000/ws by default.
  3. After changing anything under RoRebuildServer/GameConfig/ServerData (monsters, items, maps), run .\rr update-client so the client config matches.
The server data uses custom monsters with IDs of 6000 and up whose sprites aren't in any official client (Doddler's README, "Special Considerations"). The fork's pack has Doddler's real sprites in its Custom folder (above). Without them, each one gets a stand-in: upstream's own aliases, plus fungus → poison_spore.

Build the client

.\rr build-client      # Windows x64 player into buildOutput (workDir\Build\PC)
.\rr play              # launch it (start .\rr server first)
.\rr smoke             # automated end-to-end check of the build

This runs unity build --target StandaloneWindows64 --execute-method ...BuildWindows. The build converts any sprites still missing their data, refreshes addressable groups, builds addressable content (~13 min here), then builds the player with Assets/Scenes/MainScene.unity (~5 min the first time, ~2 min after). The project's player backend is IL2CPP, which is why the Windows IL2CPP module and an MSVC toolchain are prerequisites. The result is 2.5 GB, or 3.7 GB with every map baked. IL2CPP's ~1 GB of debug output is moved to Build\PC-symbols, so the PC folder can be zipped and shared as is; rr release packages it with a server.

A build records the editor version and the name, size and time of every file in ProjectSettings, Packages and Assets, so rr build-client with none of them changed returns in about 5 seconds instead of rebuilding (-Force builds anyway). A file changed while the build ran, other than the settings and addressable groups the build rewrites itself, makes the next one build again.

rr smoke checks a build for real. It starts the server with the pack's walk data (unless one is already on port 5000), then launches the build windowed with -rrSmokeTest. The player creates a throwaway account and character through the normal login flow, waits for the world to load, saves a screenshot to workDir\smoke\ and quits with exit code 0 or 1. rr prints the steps, plus any exceptions from the player log. It takes about a minute; here it lands a Novice on prt_fild08 with the map, sprites, UI and minimap loaded. To land somewhere else, set the server's start position in the same PowerShell first, for example $env:ServerCharacterEntry__Map = "yuno"; $env:ServerCharacterEntry__X = 158; $env:ServerCharacterEntry__Y = 20; $env:ServerCharacterEntry__Area = 0. It only reaches a server rr starts, and a start cell inside a warp moves the character on before the screenshot.

The built client connects to the address in the login window's Server tab. It defaults to ws://127.0.0.1:5000/ws and is remembered between runs, so to play against another machine you just type its address there. Play mode in the Editor uses the same login window. (NetworkManager.BeginConnection and serverconfig.txt are leftovers upstream no longer calls.)

Why builds switch the addressables profile. The committed active profile is "Default", which loads the remote catalog from https://www.dodsrv.com/[BuildTarget], Doddler's live server. A plain build would try to stream content from there. The automation temporarily switches to the repo's "Local" profile so all content ships inside the build, then restores the committed setting.

Share a release

.\rr release           # build the player, then package and check it into workDir\release
.\rr release -NoBuild  # package the current player build instead

rr release makes a download for people who only want to play, in the same layout as Doddler's (Client, Server, readme). It's named after the date and commit, for example RagnarokRebuild-2026-10-01-b7863217, and holds:

  • Client\: the player build, without its debug symbols.
  • Server\: a self-contained publish that carries .NET 9, so nothing needs installing. It comes with ServerData, the pack's walk data for 272 maps and the compiled script cache. Only appsettings.json and appsettings.Logging.json ship, pointed at the folders beside the exe; the Production settings add an https endpoint on port 443 that needs a certificate. /adminify is on, with a passcode picked at random for each release.
  • Play.cmd: starts the server in its own window unless one is already running, waits until it accepts connections, then starts the client.
  • readme.txt: how to play, the passcode and Doddler's admin commands, resetting, LAN play. version.txt: the commit, the client build, the .NET version and the pack signature it was made from.

Before archiving, rr runs the smoke test on the release itself: its own server exe from its own folder, with the client from its Client folder, so port 5000 has to be free. Unlike rr smoke, any error in the player log fails it. It then deletes the database, keys and logs the test left behind, and 7-Zips the folder (a zip without 7-Zip) next to a .sha256 file. With -NoBuild the whole run took 7 minutes here and made a 3.86 GB folder and a 2.25 GB archive; Doddler's June 2025 download is 2.6 GB, with a .NET SDK installer in it. Extracted into another folder (2 minutes), Play.cmd had the server up and the client open in 18 seconds.

Profiles live in RebuildClient/Assets/StreamingAssets/ProjectConfig/*.json (see Docs/MINIMAL_DEVELOPMENT.md). Running a bigger profile later keeps what's already there, and a rerun after an interruption continues where it stopped, because the importers skip scenes and files that exist.

That skipping also means a changed pack file would never reach a project imported before the change, so rr keeps records of each import in Assets/Scenes/Maps/.rr-import/ (gitignored, and Unity ignores dot folders): the pack's files with their hashes, and for each imported asset a stamp of the pack files it's made from (deps.tsv). Before Unity starts, rr import deletes the assets whose stamp changed and the project's copies of sprite and palette files that changed, with their sprite data. Their .meta files stay, so the remade assets keep their GUIDs. It also removes converted files the pack no longer makes, and names any map that left the pack without deleting it. Swapping one map's ground file re-imported just that map, in 1.5 minutes. When the pack and the imported folders are as the last finished import left them, rr import returns without starting Unity; -Force runs the importer anyway. A project imported before these records existed is taken as imported from the current pack.

Two things the upstream importer can't repair by itself, rr handles on every run:

  • Sprites left unconverted. An .act is turned into sprite data only in the refresh that imports it. If Unity dies mid-import, the next run finds those .act files already imported and never converts them, so the monsters stay invisible. rr import, rr addressables and rr build-client convert any sprite missing its data first; rr report shows the count (0 here, 4,377 sprite data assets).
  • Changed sounds. The importer skips files that already exist, so rr import copies sounds the pack added or changed itself, and queues the sprites whose sound events name them for reconversion.

Imported assets are gitignored upstream (Maps, Sprites, Sounds, Music, Models, Scenes/Maps, Effects). Maps, sprites or effects you add later need .\rr addressables before they load at runtime.

Lighting & minimaps optional

Without baked lighting the maps render flat. Baking is GPU-bound: the first 233 maps took 5 hours here on an RTX 3090 (a median of 78 seconds per map, up to 3.5 minutes for pay_fild01) and wrote 2.9 GB of lightmaps (a median of 7.5 MB per map, up to 62 MB for c_tower1). It's a separate step, and it resumes where it stopped:

.\rr bake prt_fild08,prontera   # try a couple of maps first
.\rr bake                       # every map without lighting from its current scene (resumable)
.\rr bake prontera -Force       # re-bake a map (e.g. a washed-out lightmap, a known upstream issue)
.\rr minimaps                   # after lighting; only maps whose scene or lighting changed (-Force: all)

rr bake drives the upstream Lighting Manager's bake headlessly (ambient pass, lit pass, light probes), one map at a time, so results match the editor button. Each map is backed up first and put back as it was if its bake doesn't finish (details). Unity only bakes into the project, so lightmaps are written next to each scene in Assets/Scenes/Maps/<map>/ on the repo drive. The Library drive needs room too: Unity's imported copies of the lightmaps are much larger than the files, and during the full bake the Library grew by up to 11 GB before settling 2 GB above where it started. Minimaps took 11 minutes for those 233 maps (Assets/Maps/minimap/; 2009rwc_03, added later, took 30 seconds to bake and 10 to draw); without one the client just logs a missing-key error for that map. A scene imported again starts without lighting, even though its old lightmaps are still in its folder, so the import records also note which import of a scene each bake and minimap was made from: after rr import remakes a map, rr bake and then rr minimaps redo just that map (prt_fild08 took 2 minutes to bake and 20 seconds to draw), and with nothing to redo each returns once Unity has started. Rebuild the player so the lighting and minimaps ship; the build registers new minimaps itself, and rr addressables does it for Play mode in the editor. Save a snapshot afterwards; it's what you share to spare others the bake (above).

Snapshots (fast reinstall)

A full import takes an hour and a half. A snapshot keeps its result so you never repeat it: the imported folders (Sprites, Sounds, Maps, Models, Scenes/Maps, Effects, Textures/Import, Music), the tracked files the importers regenerated, and the Library's import state.

.\rr snapshot save              # after an import or bake (12.5 min and 15 GB after the import; 19.8 GB baked)
.\rr snapshot list
.\rr snapshot restore           # into this clone (7.5 min here), then open Unity as usual
.\rr snapshot save -Name baked  # keep several; -NoLibrary skips the Library (Unity then reimports once)
  • Tested on a fresh clone on another drive: after restore, Unity opened the project in under a minute without reimporting (35 small imports), with the same counts as here (233 maps, 4,377 sprite data assets, 3,245 sounds).
  • rr setup restores the latest snapshot by itself into a clone that hasn't been imported yet, when the snapshot was saved from the same pack or carries the import records. Setup then imports, which brings in only what the pack changed since the snapshot was saved. An older snapshot of a different pack is left alone, and setup imports from scratch.
  • Build caches (BuildCache, Bee, built bundles, ~25 GB after two player builds) are left out, and a restore doesn't delete a machine's own copies of them.
  • The generated client config (StreamingAssets/ClientConfigGenerated) isn't in a snapshot, because it's derived from the server data; rr regenerates it the first time Unity runs.

Known gaps

  • 2009rwc_03 (a debug room) is the one client map no client has, under any name, not even the September 2009 client. The fork's pack has it from the Custom folder (above). Built without it, the server still gets its walk data from the release, but the client can't render it.
  • izlude, alberta, moc_ruins need an old client: the 2009 client for izlude and alberta, the classic client for moc_ruins. The classic client's izlude and alberta come close (404 and 5 cells off). Every current kRO client has the redrawn versions: 23 of izlude's 39 script positions (NPCs and warp arrivals) land on blocked cells there, and 3 of alberta's 59. Without an old client, the pack takes kRO's versions and builds the server's walk data from them, so the client and server still agree.
  • que_qsch01: every client ships a version 2,837 cells off Doddler's. The fork's pack has his edited map from the Custom folder (above). Built without it, the server gets walk data built from the client's map, so the two still agree.
  • JunoClouds, the cloud layer Doddler placed by hand in his yuno and que_qsch01 scenes (the only two of his release's 231 that have it), is left out on purpose. No map file describes it, so the importer never adds it. The prefab is in the repo: dropping it into a scene in the editor brings it back. He used the prefab as is in yuno and lowered it from −6.5 to −4.6 in que_qsch01; it follows the camera, so only the height matters.
  • Server-only custom maps rebuildtower, sword_1-1, turbo_n_1 are newer than the June 2025 release and in no client. The server logs a missing walk file and falls back to an open grid; nobody can enter them from the client either way. (pvp_n_1-5_ reuses pvp_n_1-5.walk, which is present.)
  • The old kRO RAG_SETUP_2006/2009 installers compress their GRF, so RebuildPack --scan finds nothing inside them; they have to be installed to be used as sources. The 2009 client source is such an install's data.grf.
  • GRFs repacked with GRF Editor's custom (non-zlib) compression can't be read. Such maps are only skipped as rename candidates; nothing in the pack comes from them.
  • One short sound: wav\worm_tail_damage.wav's compressed stream inside kRO's own GRF is 7 bytes shorter than its declared size. It's zero-padded to the declared size, the same as GRF Editor does. The missing bytes are the end of the file's metadata text, after the audio, which is complete. Five of the six clients checked ship this same short copy.
  • rdata.grf (Renewal-only data) is ignored on purpose. Rebuild targets the classic data.grf content.

Stopping & resuming

Any rr command can be stopped (Ctrl+C, a closed terminal, a crash, a power cut) and simply run again. The rerun carries on where it stopped and never trusts a half-written file. rr doctor lists anything left half done under "Interrupted work", and every command prints the same notes before it starts.

StepWhat the rerun does
rr packCarries on from manifest.partial.jsonl, the list of files the stopped run finished. Files are written to a temp file, flushed and renamed into place, and a file is only reused while its size and timestamp still match what the manifest recorded.
rr importDeletes the files Unity was still copying (a cut-off copy is full size but ends in zeros) and any generated file it left damaged. The map whose scene it saved last is imported again, because that map's other assets may not have reached the disk. Assets it deleted to bring in pack changes are made by the rerun, since the import records count an import as finished only once Unity has. Bake, minimaps, build and snapshot save wait until the import has finished.
rr bakeBefore each bake, the map's scene, lighting folder and probe texture, plus the shared lighting settings, are copied to Library\rr-journal\bake-backup. A map whose bake was cut off (or failed) goes back exactly as it was, then the queue carries on. Any Unity command puts it back first (rr report, rr build), so a half-lit map never ships.
rr minimapsCarries on with the maps it had left.
rr build, rr referenceBuilt or extracted beside the old folder (.new) and swapped in only once complete. rr play and rr smoke never start a half-built player.
rr snapshotA save marks itself complete last. list shows an incomplete one as such, and it can't be restored. Rerunning a save or a restore resumes it (robocopy skips what is already copied and recopies the file it was cut off in). Unity commands refuse to run on a half-restored project.
rr library-linkFinishes the move to the same destination. Unity commands refuse to run until it has.
rr syncPuts back the regenerated files it set aside for the merge (.git\info\rr-generated-backup).
rr install-unityRepairs the editor or the IL2CPP module instead of trusting what's on disk, reusing the downloads.
rr prereqs, bootstrapChecks again and installs whatever is still missing; a tool winget already finished counts as present. The bootstrap reuses the clone, or clones again if the first one was cut off before its checkout.
rr smokeStops the test server the stopped run left behind.
rr releaseStarts over: stops the stopped run's test server and deletes its half-made folder or archive, which are only renamed into place once complete.

Only one state-changing rr runs at a time; a second one refuses and names the command holding the lock. doctor, disk, server, play, smoke and editor run alongside, so you can check on an overnight bake. The records live in .git\info\rr-state (rr) and Library\rr-journal (Unity) and are removed once their step finishes.

Tested by killing rr pack (resumed 6,370 of 25,001 files, then rewrote nothing), rr bake after its first pass (the map came back byte-identical), rr snapshot save at 1.5 GB and rr reference mid-extraction, and by staging what a cut-off import, minimaps run and sync leave behind.

"winget is missing"App Installer isn't installed or not registered yet (a fresh Windows registers it after the first sign-in and a Store update). Install App Installer from the Microsoft Store, or install the tools from the links rr prints, then rerun.
".NET 9 SDK missing" although dotnet --version worksOnly a newer SDK is installed. The server and tools need the .NET 9 runtimes; rr prereqs installs the 9 SDK alongside it.
A tool was installed but rr can't find itrr adds new PATH entries from the registry every time it starts, so a new terminal isn't needed. If it still isn't found, the installer didn't add it to PATH; rr doctor shows which tool.
Unity install fails, "installer exited with code 2"The MSIX (winget) Unity CLI. Run rr install-unity, which replaces it.
"RebuildClient is open in a Unity Editor"Batch mode needs exclusive access. Close the editor and rerun.
Batch run fails with license errorsunity auth login, then unity license activate --personal --accept-eula (or rr install-unity).
rr pack reports unresolved referencesOpen packDir\report.html → Issues. Add a client that has the file as another pack source, drop the file into the Custom folder, or add a stand-in to setup\pack\aliases.json with a reason.
A map looks wrong in gameCheck it in the report's map table: source, RSW version, whether it was converted and how its walk data compares with the release.
git status full of ProjectSettings/asset changes with no diffcore.autocrlf=true vs Unity's LF writes. rr git-setup sets input. For real regenerations use rr generated hide.
GameConfig.dll / RebuildSharedData.dll modifiedRebuilt DLLs never match byte for byte. rr update-client restores the committed ones unless you changed shared code (-KeepDlls keeps them).
Effects are white rectanglesRagnarok > Import and Update Skill Effect Atlas (the full import already runs it).
Item sprite errors when logging inRagnarok > Import Skill and Item Icons, then rr addressables.
New sprites/maps don't load at runtimerr addressables after adding them.
Build fails with "Unable to build with the current configuration" / SBP ErrorExceptionThe Windows IL2CPP module is missing (the editor alone only has Mono). rr install-unity adds it; rr doctor checks it.
Monsters or equipment invisible in gameSprites without sprite data, usually after an interrupted import. rr import (or rr addressables) converts them; rr report should show "0 sprite(s) unconverted".
Import log: "Sprite file is missing: 1_남_1.spr" … "1_여_8.act" (32 lines)Expected. Upstream's check looks for the default hairstyle's colours as sprite files, but they're palette variants the importer builds (1_남_1.asset …).
Where are the logs?Unity: RebuildClient\Logs\rr-<step>.log. Server: RoRebuildServer\RoRebuildServer\Logs. rr prints the relevant lines live.
